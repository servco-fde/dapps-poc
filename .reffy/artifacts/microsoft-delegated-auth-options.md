# Microsoft delegated access: direct app flow or Databricks-managed connection

Exploration for Metric View Hub, 2026-10-15. This is a decision aid, not an approved implementation or a replacement for `add-microsoft-delegated-connection`. No app registration, Unity Catalog connection, permission, secret, or deployment was changed.

## Discussion summary and organization constraint

Connecting Metric View Hub to the Azure registration with a client secret proves **app-only** access; it does not activate that registration's delegated permissions for each Databricks App user. A user-scoped Graph `/me` call needs a separate per-user authorization step even though Databricks and Microsoft share Entra ID. There is no setup-free path where the existing secret automatically carries the logged-in user's Microsoft permissions.

For the **direct** route, the registration owner would add exact Web callback URL(s), and Metric View Hub would implement the user sign-in/callback and request delegated `User.Read`. For the **Databricks-managed** route, Databricks would own the callback and Microsoft token lifecycle, but someone must create and govern a per-user Microsoft 365 Unity Catalog HTTP connection. A manually configured Databricks connection using the existing registration combines these approaches, but still needs a Databricks callback URL on that registration.

Roberto reports that, in this organization, creating Unity Catalog connections or holding metastore-admin rights is reserved exclusively for administrators. Thus the managed and manual-connection routes both require an administrator's involvement here, even though Databricks generally also permits a non-admin who has been delegated `CREATE CONNECTION`. The managed provider may additionally require Microsoft tenant consent for its broader scopes; that has not been checked with the organization. The direct route still requires coordination with the registration owner, but appears to be the smaller setup request for a profile-only proof. This is a **provisional preference**, not a completed connection or an instruction to bypass organization policy.

## What the current prototype proves

The server's client-secret flow obtains an **application** token. It can retrieve a profile photo under the registration's `ProfilePhoto.Read.All` application role, but the live `/users/{email}` text request returned 403. It cannot call Graph `/me`, which requires a user-delegated token. The existing registration screenshot shows delegated `User.Read`, but that permission is not exercised by the app-only token. [Graph Get user](https://learn.microsoft.com/en-us/graph/api/user-get?view=graph-rest-1.0).

## Two primary options

| Decision point | Direct Microsoft sign-in with existing registration | Databricks-managed Microsoft 365 OAuth |
| --- | --- | --- |
| User journey | `Connect Microsoft` in Metric View Hub redirects to Entra, then back to the app. | User authorizes a Databricks-managed Microsoft 365 HTTP connection on first use; Metric View Hub can present a connect state, but the exact first-use link/error handoff must be tested. |
| Redirect | Registration owner adds exact Web callback(s) for local and deployed app URLs. | No callback on the colleague's registration. Databricks uses its own managed redirect; a tenant policy may still require allowing that URL. |
| OAuth client and secret | Existing `servco-adb-app-workshop-appreg-dev` client ID and server-only secret. | Databricks-managed OAuth client and credentials; the colleague's registration and secret are **not** reused. |
| Organization setup owner | Registration owner adds callback URL(s); app team implements the flow. | An administrator must create/govern the Unity Catalog connection under this organization's policy; Microsoft tenant consent may also need administrator review. |
| Graph permissions | Request only delegated `User.Read` for `/me`; later features add only required scopes. | Managed Microsoft 365 provider documents `User.Read` alongside Teams, mail, SharePoint, and write scopes. Exact consent screen scopes can change and must be reviewed before use. |
| Token handling | Metric View Hub server owns callback, state/PKCE, per-user cache, renewal, and disconnect. | Unity Catalog connection stores and refreshes external credentials; app calls Databricks' HTTP connection proxy, not Graph directly. |
| App authorization | App must bind Microsoft result to authenticated Databricks principal and keep tokens server-side. | App must call the proxy as the **forwarded Databricks user**, not its service principal, so the external per-user connection maps to the correct person. Both the user and app access model need verification. |
| Local proof | Requires registered localhost callback and MSAL Node. | Developer can likely test with their CLI user token and a dev connection; this does not prove deployed browser-user behavior. First-use flow from the React app remains unverified. |

The direct route is the cleanest fit for reusing the existing registration and limiting the profile proof to `User.Read`, but requires owner action on callback URIs. The managed route removes application OAuth code and the owner callback request; it substitutes a new Databricks-governed connection, Databricks user API access, and possibly tenant-level consent to a broader Microsoft 365 permission set. These are not interchangeable approvals. [Microsoft auth-code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow), [Databricks managed OAuth providers](https://learn.microsoft.com/en-us/azure/databricks/agents/mcp-tools/managed-oauth), [HTTP connection proxy](https://learn.microsoft.com/en-us/azure/databricks/query-federation/http).

## What the managed route would look like in this app

1. An organization-authorized administrator creates a Unity Catalog **HTTP** connection with **OAuth User to Machine Per User** and the managed **Microsoft 365 API** provider. The platform requires metastore `CREATE CONNECTION` or admin authority; this organization reserves both routes to administrators. Databricks, not Metric View Hub, handles Microsoft client credentials and the OAuth callback. [Create HTTP connection](https://learn.microsoft.com/en-us/azure/databricks/query-federation/http), [managed providers](https://learn.microsoft.com/en-us/azure/databricks/agents/mcp-tools/managed-oauth).
2. Grant intended users `USE CONNECTION`. Add that connection as a Databricks App resource, which grants the app service principal `USE CONNECTION` and injects its name; this app-resource grant alone must **not** be mistaken for per-user Graph authorization. The existing bundle requests only the Databricks `sql` user API scope; the proxy path likely needs `catalog.connections`, subject to a live scope check. [App connection resource](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/databricks-apps/connections), [Databricks App user scopes](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/databricks-apps/auth).
3. For a signed-in request, the server calls `.../api/2.0/unity-catalog/connections/<name>/proxy/me` with the user's **Databricks forwarded access token**. That token is valid for the Databricks workspace proxy, which injects the user's managed Microsoft Graph credential into its outbound request. It must not be sent straight to Graph. The proxy's host/base-path configuration must resolve `/me` to `https://graph.microsoft.com/v1.0/me`. This is an architectural inference from the proxy and App authorization docs, not yet a tested call. [HTTP connection proxy](https://learn.microsoft.com/en-us/azure/databricks/query-federation/http), [Databricks App user authorization](https://learn.microsoft.com/en-us/azure/databricks/dev-tools/databricks-apps/auth).
4. The React page shows `Connect Microsoft` if the user's connection is not authorized, then retries `/me` after the Databricks-managed login. The exact URL/status contract for first-use authorization must be discovered in the dev workspace before promising a seamless in-app button. Keep the response limited to the current user's selected fields and optional photo; do not expose the forwarded Databricks token or raw proxy errors.

## A useful middle option

A **manually configured** Unity Catalog per-user HTTP connection could reuse the colleague's existing Entra client ID/secret and request only `User.Read`, while Databricks handles token storage and renewal. It still needs the registration owner to allowlist the Databricks OAuth redirect (documented as `<workspace>/login/oauth/http.html` for manual per-user connections), so it does **not** avoid a registration change. It may simplify app code while preserving the chosen registration. Confirm the exact redirect shown by the workspace UI before asking the owner to add it. [HTTP connection authentication methods](https://learn.microsoft.com/en-us/azure/databricks/query-federation/http).

## Decision gates before changing the proposal

- Can the dev workspace create a managed Microsoft 365 HTTP connection, and can intended users authorize it under tenant policy? No connection has been created or tested here.
- Would an organization administrator sponsor and govern that connection? Roberto cannot self-provision it under the stated local policy.
- What exact scopes would its Microsoft consent screen request? The documented provider includes broad read/write scopes, not just profile `User.Read`; tenant security review may reject that for a simple profile card.
- Can a Databricks App call the per-user connection proxy with its forwarded user token and `catalog.connections` scope? Verify both `USE CONNECTION` grants, the scope allowlist, and the first-use login link/error behavior with a read-only `/me` call.
- Can local development exercise the connection with the selected `hawaii-dev-workspace` profile and `metric_hub_local_roberto` without changing shared app resources? A local developer-token success is not a second-user deployed isolation test.
- If the managed provider is unsuitable, would the owner rather add app-specific Web callbacks for the direct flow, or a Databricks workspace callback for the manual connection?

Provisional preference after the organization-policy clarification: prioritize asking the existing registration owner for direct Web callback URL(s) and using least-privilege `User.Read` for the profile proof. Keep managed OAuth as a comparison option if an administrator is willing to provision it and its consent scopes pass review. Do not silently switch the existing ReffySpec proposal to a different OAuth client.
